# Local Codex Review Usage Closeout Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the `/daily` Local Codex AI review path count as successful only when a generated answer, saved assistant record, and reflected usage event are all proven without enabling SaaS API generation.

**Architecture:** Keep official evidence retrieval and record persistence in `architect-saas`, keep generation in `architect-browser-assistant` through the page/content-script/background/native-host bridge, and persist only metadata-only Local Codex usage events back to SaaS. The first prerequisite is to make the browser bridge explicitly ready for the exact target origin: content script injected, extension loaded, native host registered, and Codex CLI available. Only after that gate passes should the SaaS page retrieve evidence, request Local Codex generation, save the assistant record, record usage, and refresh the usage summary. SaaS API policy and provider activation remain out of scope.

**Tech Stack:** Next.js App Router, React client state, TypeScript validators, Prisma/Postgres plus local repository parity, Chrome MV3 content script/background messaging, Node native messaging host, PowerShell/browser verification.

## Observed Failure Diagnosis To Preserve

The failed `/daily` run reached evidence retrieval and then timed out waiting for `architect:page-local-runtime-response` during Local Codex generation. That error is generated by the SaaS page when no page bridge response arrives.

This points first to a page bridge attachment problem, not a generated-answer or usage-recording problem:
- If the content script is not injected into the exact current origin, the SaaS page posts `architect:page-local-runtime-request` and no one answers.
- If the content script is injected but the native host is missing, the background service worker should still answer with `available: false` or a native-host error message.
- Therefore the first execution hypothesis is: the current authenticated browser tab does not have an active Browser Assistant content script for the canonical Preview origin.

Likely concrete causes to classify before coding:
- The browser surface used for verification is not the Chrome profile where the unpacked Architect Browser Assistant extension is installed.
- The installed unpacked extension bundle is stale and was not reloaded after rebuild.
- `dist/manifest.json` or the installed extension content-script match list does not include `https://architect-start2-git-codex-multi-d1c003-chois-projects-7b2948cf.vercel.app/*`.
- The extension id registered in the native-host manifest does not match the installed Chrome extension id.
- The native-host registry/launcher/Codex CLI path is broken. This is a second-stage cause only if the content script ready signal is present but `status` returns unavailable.

The implementation must not proceed directly to usage recording until this cause is classified and the matching fix is verified on the exact target browser and URL.
