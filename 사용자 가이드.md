# Architect Browser Assistant 사용자 가이드

작성일: 2026-05-11

## 기본 방향

기본 작업 화면은 SaaS `/daily` 페이지 안의 우측 하단 `AI 검토` 팝업입니다. 사용자는 일일 목록에서 task를 클릭하고, 같은 화면 안에서 건축 task 검토 질문을 입력해 답변과 의견을 받습니다.

Chrome 확장 사이드패널은 숨겨진 보조 기능입니다. 평소에는 사용하지 않고, Local Codex native host 연결 상태를 확인할 때만 수동으로 엽니다.

모바일 UX는 이번 범위가 아닙니다. 현재 구현은 PC 브라우저 우선입니다.

## 바로 실행하기

PowerShell에서 반드시 repo 폴더로 이동한 뒤 실행합니다.

```powershell
cd D:\architect-workspace\architect-saas
npm run dev
```

브라우저 주소창에 다음 주소를 직접 입력합니다. PowerShell에 URL을 명령처럼 입력하면 실행되지 않습니다.

```text
http://localhost:3000/daily
```

포트 3000이 이미 사용 중이면 Next.js가 3001 같은 다른 포트를 안내합니다. 그 경우 터미널에 표시된 `Local:` 주소를 브라우저 주소창에 입력합니다.

## `/daily` AI 검토 팝업 사용

1. `/daily`에 접속합니다.
2. 일일 목록에서 검토할 task row를 클릭합니다.
3. 우측 하단 `AI 검토` 버튼을 눌러 내부 팝업을 엽니다.
4. 질문과 검토 지침을 입력하거나 수정합니다.
5. 실행 모드를 선택합니다.
6. `근거 조회 + 의견 생성`을 누릅니다.
7. 답변, 근거, draft summary를 확인합니다.
8. 필요한 경우 `작업 기록 승인`으로 task 기록 정리 초안을 승인합니다.

## 최근 검토 기록 확인

`AI 검토` 팝업을 열면 선택된 task의 `최근 검토 기록`이 먼저 표시됩니다. 이 영역은 최근 assistant 기록을 최대 12건까지 조회하고, 팝업 안에서는 최신 4건을 카드로 보여줍니다.

각 기록 카드에서 확인할 수 있는 항목:

- 실행 모드: `Local Codex`, `SaaS API`, `Mock`, `Evidence only`
- 실행 경로: `extension bridge`, `SaaS popup`, `daily popup`, `external evidence`
- 저장 시각, confidence score, evidence 개수
- draft summary 결론 또는 답변 미리보기
- cleanup/candidate 상태와 evidence 종류

Local Codex가 정상 실행되어 저장된 기록은 `Local Codex / extension bridge`로 표시됩니다. 따라서 일일 목록을 떠나지 않고도 해당 task가 실제 PC Local Codex 경로로 검토되었는지 확인할 수 있습니다.

## 작업 기록 승인 게이트

assistant 답변이 생성되면 `작업 기록 정리 초안` 영역이 표시됩니다. 이 초안은 바로 승인되는 값이 아니며, 사용자가 결론, 태그, 적용 범위, 후속 조치를 확인하거나 수정한 뒤 저장합니다.

승인 전 필수 확인 항목:

- `Conclusion`: 작업 기록에 남길 결론이 있는지 확인합니다.
- `Scope`: 이 정리가 적용되는 task 또는 범위가 명확한지 확인합니다.
- `Evidence`: assistant record에 근거가 연결되어 있는지 확인합니다.
- `Confidence`: 신뢰도 점수와 산정 사유가 저장되어 있는지 확인합니다.
- `Follow-up`: 다음 확인 조치 또는 종결 사유가 적혀 있는지 확인합니다.

모든 필수 항목이 `pass`일 때만 확인 체크박스를 선택할 수 있고, 체크 후 `작업 기록 승인`을 누를 수 있습니다. 아직 승인하기 어렵다면 `보류 저장`으로 deferred 상태를 남깁니다.

## 승인 후 task 반영 제안

`작업 기록 승인`이 완료되면 같은 팝업 안에 `Task 반영 제안` 영역이 표시됩니다. 이 영역은 승인된 assistant 요약을 실제 task에 옮기기 위한 선택 단계이며, 승인만으로 task가 자동 수정되지는 않습니다.

제안 액션:

- `task 기록 업데이트 적용`: 승인된 결론, 범위, 후속 조치, 태그를 task decision에 추가합니다. task가 아직 `new` 상태이면 보수적으로 `in_review`로만 올리고, 다른 상태는 유지합니다.
- `후속 task 생성`: 승인된 후속 조치를 parent task 아래 child task로 생성합니다.

각 액션은 별도 버튼을 눌러야 실행됩니다. 둘 중 하나만 적용하거나 둘 다 적용하지 않을 수 있습니다.

## assistant 출처 표시

assistant 승인 요약으로 task decision을 업데이트하거나 후속 child task를 만든 경우, `/daily` 작업 상세 패널에 `AI provenance` 영역이 표시됩니다.

- parent task에는 승인된 assistant summary record id와 assistant가 만든 follow-up task 번호가 표시됩니다.
- follow-up child task에는 source assistant record id와 parent task 참조가 표시됩니다.
- 이 영역은 읽기 전용 추적 정보이며, 기존 task 편집/저장 방식은 바꾸지 않습니다.

## 실행 모드

- `Mock`: 개발/검증용 deterministic 응답입니다.
- `SaaS API`: 서버 정책, 사용량 기록, 감사 로그를 거치는 조직 단위 실행 모드입니다.
- `Local Codex (extension)`: 현재 PC의 Chrome 확장, native host, Codex CLI를 통해 생성합니다.

`Local Codex (extension)` 모드는 SaaS 서버나 브라우저 저장소에 Codex/OpenAI credential을 저장하지 않습니다. 선택된 task context, 질문, 검색된 evidence만 extension bridge로 전달합니다.

## Local Codex extension 설정

확장 repo에서 빌드와 native host self-test를 실행합니다.

```powershell
cd D:\architect-workspace\architect-browser-assistant
npm run native-host:self-test
npm run build
```

Chrome 설정:

1. `chrome://extensions`를 엽니다.
2. Developer mode를 켭니다.
3. `D:\architect-workspace\architect-browser-assistant\dist` 폴더를 `Load unpacked`로 불러옵니다.
4. 생성된 extension id를 복사합니다.
5. 같은 repo 폴더에서 native host를 등록합니다.

```powershell
cd D:\architect-workspace\architect-browser-assistant
npm run native-host:install:windows -- -ExtensionId <chrome-extension-id>
```

실제 Codex 호출 없이 smoke test만 하려면 `-Mock`을 붙입니다.

```powershell
npm run native-host:install:windows -- -ExtensionId <chrome-extension-id> -Mock
```

설치 경로를 한 번에 검증하려면 verifier를 실행합니다.

```powershell
npm run native-host:verify:windows -- --extension-id <chrome-extension-id> --strict
```

현재 이 PC에서는 extension id `ianebfgjhjklildppcocmbmifedapooj` 기준으로 HKCU native host registry, manifest, launcher, mock native host status, Codex CLI status가 모두 pass로 확인되었습니다.

등록 후 Chrome extension을 reload하고 `/daily` 페이지도 새로고침합니다. 그 다음 내부 `AI 검토` 팝업의 실행 모드에서 `Local Codex (extension)`을 선택합니다.

## Local Codex 상태 점검

`/daily` 내부 팝업에서 실행 모드를 `Local Codex (extension)`으로 바꾸면 `Check bridge` 버튼이 보입니다.

1. `Check bridge`를 누릅니다.
2. `Extension bridge`가 `pass`면 현재 `/daily` 페이지의 content script가 응답한 것입니다.
3. `Native host / Codex`가 `pass`면 native host와 Codex CLI가 생성 가능한 상태입니다.
4. `Native host / Codex`가 `fail`이면 표시된 reason을 보고 native host 등록, Codex CLI 설치, Codex login 상태를 확인합니다.
5. `Extension bridge`가 `fail`이면 확장을 rebuild/reload한 뒤 `/daily`를 새로고침합니다.

체크리스트가 모두 `pass`일 때 `근거 조회 + 의견 생성`으로 실제 Local Codex 생성을 시도합니다.

## Chrome 사이드패널의 역할

사이드패널은 기본 UI가 아닙니다. 정상 작업은 `/daily` 내부 팝업에서 진행합니다.

사이드패널을 수동으로 열어야 하는 경우:

- native host가 등록되어 있는지 확인할 때
- Codex CLI 설치 또는 로그인 상태 오류를 볼 때
- extension service worker와 native messaging 경로를 진단할 때

사이드패널에서 `Current page is not a supported task view`가 보여도, `/daily` 내부 팝업이 task를 선택하고 동작하면 정상 작업 흐름에는 문제가 없습니다. 사이드패널은 페이지 탐지 진단용이고, 기본 task 검토는 SaaS 내부 선택 상태를 기준으로 동작합니다.

## SaaS API Mode 관리

관리자 화면:

```text
http://localhost:3000/admin/assistant
```

여기에서 SaaS API Mode enabled 상태, provider, model, token 제한, 월 예산, 허용 evidence type, usage ledger, audit timeline을 확인합니다.

`Assistant action audits` 영역에서는 assistant 승인 요약으로 실제 task에 반영된 변경을 구조화된 감사 기록으로 확인합니다.

- `Action`: task update 적용과 follow-up task 생성을 구분합니다.
- `Task ID or title`: task id, 표시 번호, 제목으로 관련 기록을 좁힙니다.
- `Assistant record`: 원본 assistant record id 일부로 필터링합니다.
- `Actor`: 기록을 만든 사용자/profile id로 필터링합니다.
- `Open task`: 해당 기록의 대상 `/daily` task를 열고 PC 상세 패널을 펼칩니다.

`openai` provider를 사용할 때 서버의 `OPENAI_API_KEY`가 없으면 생성 요청은 안전하게 실패로 기록됩니다. 브라우저에는 credential이 노출되지 않습니다.

## 문제 해결

- `npm`이 `C:\WINDOWS\system32\package.json`을 찾는 오류: repo 폴더로 이동하지 않은 상태입니다. `cd D:\architect-workspace\architect-saas` 또는 `cd D:\architect-workspace\architect-browser-assistant`를 먼저 실행합니다.
- URL을 PowerShell에 입력했을 때 cmdlet 오류: URL은 명령이 아닙니다. 브라우저 주소창에 입력합니다.
- `Path 매개 변수가 빈 문자열` 오류: install script를 잘못된 위치에서 실행했거나 script context가 없는 방식으로 호출된 경우입니다. `architect-browser-assistant` repo에서 `npm run native-host:install:windows -- -ExtensionId <id>`로 실행합니다.
- `Local Codex extension bridge did not respond`: extension을 rebuild/reload했는지, `/daily`를 새로고침했는지, content script가 해당 origin에 로드됐는지 확인합니다.
- native host 오류: extension id로 Windows native host를 다시 등록하고, `npm run native-host:verify:windows -- --extension-id <id> --strict`를 먼저 확인합니다.
## Structured action audit notes

- When `Structured audit records` appears in `/daily` task detail, the app is reading saved assistant action audit events for task updates and follow-up task creation.
- Existing decision/note text markers remain as a fallback for older assistant-origin task changes.
- In `http://localhost:3000/admin/assistant`, the `Assistant action audits` section now has an `Export CSV` link.
- The export uses the same month, action, task, assistant record, and actor filters currently shown in the review list.
- The CSV is read-only audit evidence and includes task links, assistant record ids, actor ids, summary fields, status transition fields, tags, and decision markers.
- Each assistant action audit card also has a `Review details` button.
- `Review details` opens a read-only governance panel with the raw audit event, assistant record id/mode/confidence/evidence count, closure summary fields, source/target/created task snapshots, task history, provenance, and a `/daily` detail link.
- The same panel has an `Export package` link. It downloads a read-only Markdown evidence package for that one audit record.
- The package includes audit event fields, assistant record summary, closure fields, task snapshots, provenance, governance notes, and raw audit metadata.
- In the same `Review details` panel, admins can append a governance note.
- Governance notes require a category and note text, store reviewer id and timestamp, and appear under `Governance notes` after saving.
- Notes are append-only review events; they do not edit or delete the original assistant action audit metadata.
- The `Governance note report` section in `http://localhost:3000/admin/assistant` lists notes across assistant action audits.
- The report can be filtered by month, category, reviewer, task id/title, and assistant record id.
- `Export notes CSV` downloads the filtered note report with note category, reviewer, timestamp, source audit id, assistant record id, task labels, daily task link, and note text.
- Each report card has `Review audit` for the source audit drill-down and `Open daily detail` for the linked task.
- The `Audit retention preview` section shows the current assistant retention policy, a read-only preview retention window, cutoff time, protected count, eligible count, and monthly counts for assistant action audits and governance notes.
- Changing `Preview retention days` only recalculates the preview. It does not save policy changes and does not delete records.
- `Export archive preview` downloads a read-only JSON archive preview that preserves raw metadata plus normalized action audit or governance-note context before any future cleanup is allowed.
- The archive preview includes an `archivePreviewToken`. Guarded cleanup requires the same token, the same cutoff, and the exact confirmation text `DELETE_ASSISTANT_AUDIT_EVENTS`.
- `Run cleanup` deletes only records currently eligible under that preview and then writes a cleanup audit event with deleted and skipped ids.
- If the preview has no eligible records, cleanup stays disabled in the Admin UI.
- The `Cleanup history` section lists cleanup audit runs separately from retention preview counts.
- Cleanup history can be filtered by actor, cutoff, and preview token, and `Export cleanup CSV` downloads deleted/skipped id metadata for review.
- `Dry-run comparison` compares a previous cleanup token with the current retention preview and shows newly eligible, previously deleted/skipped, and still protected counts without deleting records.
- `Export comparison JSON` downloads the read-only comparison result before another cleanup run.
- Each cleanup history card has `Review cleanup` for a read-only drill-down with raw cleanup metadata and `Export package` for a Markdown evidence package.
- Cleanup detail and package export rely on the cleanup audit event itself, so they still work after source action/governance audit events have been deleted.
- In `Cleanup detail`, admins can append a category-based cleanup review note.
- Cleanup review notes store reviewer id and timestamp, appear under `Cleanup review notes`, and are included in that cleanup run's Markdown package.
- Cleanup review notes are separate append-only audit events. They do not edit cleanup metadata and are not included in retention action/governance cleanup eligibility.
- The `Cleanup review-note report` section lists cleanup review notes across cleanup runs.
- The report can be filtered by month, category, reviewer, preview token, and cleanup id.
- `Export cleanup notes CSV` downloads the filtered report with note text, reviewer, timestamp, cleanup id, cleanup token, cutoff, and cleanup counts.
- The same report shows read-only summary metrics: total cleanup notes, reviewed cleanup runs, unreviewed cleanup runs, total cleanup runs, category counts, and reviewer counts.
- Summary metrics use the same filters as the cleanup note report, so the counts reconcile with the visible report and CSV filter scope.
- `Export coverage CSV` downloads cleanup runs in the same filter scope with reviewed/unreviewed status, cleanup id, token, actor, cutoff, deleted/skipped counts, note count, latest note timestamp, and reviewer ids.
- The coverage dashboard cards show the same reviewed/unreviewed status on screen with cleanup token, note count, latest note timestamp, reviewer ids, and cleanup detail/package actions.
- `Export coverage JSON` downloads a read-only machine-readable evidence package with filters, summary counts, category/reviewer counts, and coverage rows.
- `Stale days` marks unreviewed cleanup runs older than the threshold as `stale review alert` and shows a `Stale unreviewed` summary count. This is read-only and does not change cleanup metadata.
- `Export rollup package` downloads a read-only Markdown summary for monthly governance review, including filters, summary metrics, category/reviewer counts, stale counts, and cleanup coverage rows.
- `Coverage preset` switches the cleanup coverage dashboard and coverage exports between all cleanup runs, reviewed cleanup runs, and stale unreviewed cleanup runs without changing cleanup notes or cleanup metadata.
- `Copy filter handoff` copies the active cleanup coverage filter string so monthly reviewers can hand off the exact month, filters, stale threshold, and coverage preset.
- In `Reviewer counts`, selecting a reviewer count applies that reviewer id to the cleanup review filters; `All reviewers` clears it.
- In each cleanup coverage row, `Focus token` applies that row's archive preview token to the cleanup review filters.
- In each cleanup coverage row, `Focus cleanup` applies that row's cleanup audit id to the cleanup review filters.
- The `0 stale days`, `7 stale days`, and `30 stale days` buttons switch common stale-alert thresholds without changing cleanup metadata.
- `Clear cleanup filters` resets the cleanup review report to all categories, all coverage, no reviewer/token/cleanup id filter, and the default 7-day stale threshold.
- Active cleanup filter chips summarize the current cleanup review/report/export scope beneath the filter controls.
- `Show stale unreviewed` switches directly to stale unreviewed cleanup coverage with a zero-day stale threshold.
- `Show reviewed cleanup` switches directly to cleanup runs that already have review notes.
- Cleanup coverage rows are grouped into `Stale unreviewed queue`, `Other unreviewed queue`, and `Reviewed evidence queue` so monthly reviewers can triage urgent gaps separately from completed evidence.
- Each cleanup queue group shows read-only `Runs`, `Notes`, `Deleted`, and `Skipped` totals for the currently filtered coverage scope.
- Cleanup queue headers provide shortcuts: `Focus stale`, `Focus reviewed`, and `Show all coverage`.
- Cleanup queue rows show compact chips for review status, stale state, note count, reviewer count, and stale threshold.
- `Compact queue` hides secondary cleanup row details while keeping row actions and chips visible; `Detailed queue` restores the full row.
- In `/admin/knowledge`, the candidate queue shows `Candidate`, `Approved`, `Rejected`, and `All` counts before filtering.
- In `/admin/knowledge`, quick filter buttons switch between candidate, approved, rejected, and all candidate states while keeping the state select in sync.
- In `/admin/knowledge`, `Search candidates` filters the loaded queue by title, summary, task, project, or tag text.
- In `/admin/knowledge`, the WIKI draft editor shows readiness chips for title, summary, body, tags, and evidence.
- In `/admin/knowledge`, the WIKI draft editor includes a read-only `Markdown preview` of the current body draft.
- In `/admin/knowledge`, source chips show task id, assistant record id, evidence count, and publication scope beside the WIKI draft.
- In `/admin/knowledge`, freshness chips show candidate created, updated, and reviewed timestamps beside the WIKI draft.
- In `/admin/knowledge`, approval summary chips show candidate state, cleanup state, confidence, and review status beside the WIKI draft.

## Approved WIKI readback

- In `/admin/knowledge`, `Approved WIKI` shows entries that were already approved into the Knowledge WIKI.
- Use `Search approved` to find approved entries by title, summary, body text, tag, source record id, task id, or project id.
- Scope, tag, source-state, and sort controls narrow the approved list without touching database internals.
- Selecting an approved row shows approval metadata, source record/task/project ids, tags, quality checks, Markdown preview, and source references.
- Copy actions are available for approved Markdown, selected item handoff, current search handoff, source package, and filtered index package.
- If an approved item has no source references, the readback panel keeps it visible and flags the missing source state for reuse review.

## Approved WIKI export and sync readiness

- In `/admin/knowledge`, the `Export / Sync` panel prepares approved WIKI entries as portable packages.
- `Export scope` switches between the currently visible approved list and the selected approved item.
- `Package format` switches between JSON and Markdown packages.
- `Sync target` records the intended target profile: portable archive, Obsidian vault, Notion import, or assistant retrieval.
- Readiness checks flag empty export scope, missing lineage/source references, missing tags, and missing Markdown body before sync.
- `Copy sync manifest` copies target, format, filter scope, readiness, and item ids for handoff.
- `Copy export checklist` copies package stats, readiness rows, and included items.
- `Download package` creates a browser-side JSON or Markdown file. This does not write a server-side sync record yet.

## Approved WIKI guarded sync history

- `Preview sync dry-run` records a server-side audit event with target, format, scope, package name, readiness, source counts, and dry-run warnings.
- `Run guarded sync` requires the `SYNC_APPROVED_WIKI` confirmation text and all readiness checks before the server records a provider-ready or provider-blocked audit event.
- If the confirmation text or readiness is missing, the attempt is persisted as blocked instead of calling an external provider.
- Provider execution remains blocked unless the requested target is present in server sync configuration and execution is explicitly enabled.
- `Copy sync history` copies the persisted dry-run/blocked/provider status history report for review handoff.
- `Clear local history` clears only the current browser view of the history. Server audit events remain append-only and will reload from `/api/admin/knowledge/export-audits`.

## Approved WIKI provider target previews

- In `Provider target`, admins can enable the selected sync target and keep it in `Dry-run only` mode.
- `Save target config` records the selected target, dry-run-only flag, notes, actor, and timestamp as an append-only server audit event.
- `Credential reference` stores only an opaque server-side secret reference. Do not paste provider tokens, API keys, bearer strings, or raw secrets into this field.
- Target config responses show credential status, source, and scope only. Server environment references such as `env:KNOWLEDGE_SYNC_OBSIDIAN_CREDENTIAL_REF` can satisfy readiness without exposing the secret value.
- Server-side credential registry metadata can be supplied through `KNOWLEDGE_SYNC_CREDENTIAL_REGISTRY_JSON`. The Admin UI shows only opaque ref, store kind, validation time, rotation due time, rollback plan, reconciliation plan, and remote-write blockers.
- `Remote write ready` means the target is enabled, execution is allowed, a `secret_manager` registry credential exists, and rollback/reconciliation refs are configured. It does not enable live provider writes by itself.
- Obsidian live-write readiness also shows the deployment flag `KNOWLEDGE_SYNC_OBSIDIAN_LIVE_WRITE_ENABLED`. The flag is disabled by default and is never controlled from the browser.
- `Obsidian inventory manifest` accepts sanitized JSON metadata for existing vault Markdown files. The server stores path, optional item/source ids, digest, updated timestamp, and managed ownership only; file contents and raw text fields are ignored.
- When a target is enabled and not dry-run-only, the next confirmed guarded sync audit can become `provider_ready`.
- `Create provider preview` requires a provider-ready audit and the `PREVIEW_APPROVED_WIKI_SYNC` confirmation text.
- Provider previews generate adapter-specific operations and warnings without writing to Notion, Obsidian, retrieval storage, or archive delivery.
- Obsidian provider previews include a dry-run reconciliation package with planned Markdown paths, item ids, source task ids, create/update/delete/noop counts, and content digests. When an inventory manifest is present, matching paths with equal digests become `noop`, matching paths with changed digests become `update`, missing paths become `create`, and stale managed `approved-wiki/` inventory paths become `delete`.
- `Copy provider preview` copies the dry-run adapter report for review before any future external write adapter is enabled.
- `Execute adapter` requires a fresh provider preview id and the `EXECUTE_APPROVED_WIKI_SYNC` confirmation text.
- Guarded execution is currently enabled for `Portable archive` and `Obsidian vault`; both record server-side append-only audit artifacts only. Obsidian executions record a live-write preflight artifact with feature flag state, rollback/reconciliation refs, exact mutation operations, and blockers. Notion, retrieval storage, archive delivery, and real Obsidian vault writes remain disabled until their adapters are explicitly implemented.
- `Copy execution` copies the execution id, preview id, export audit id, artifact metadata, digest, and warnings for governance review.
- `Copy execution package` and `Download execution package` export a read-only JSON evidence package tied to the append-only provider execution audit id. The package includes preview, export audit, reconciliation, live-write preflight, rollback refs, warnings, and digest metadata; provider credentials and secret refs are excluded.
- `Execution package review history` lists retained provider execution packages from append-only audit records. Filter by target, execution status, artifact type, or package digest prefix. The history marks immutable server evidence separately from local browser downloads, which are not tracked by the server.
- `Add review note` appends a package review note to the selected provider execution package. The note is stored as a separate append-only audit event tied to the execution id and package digest; it does not mutate the retained execution package or change the package digest.
- `Export notes CSV` downloads the active provider execution package review-note report with note id, execution id, package digest, category, reviewer, execution metadata, filename, and note text.
- `Copy review handoff` copies the active provider execution package review filters, summary counts, reviewer counts, and coverage rows as Markdown for external review context.
- Review-state, reviewer, note-type, stale-days, and digest filters are read-only. They narrow the package review report and coverage queue without creating provider writes or changing package evidence.
- Package digest quick filters and note-category summary chips apply the same read-only review filters without typing; they do not mutate retained execution packages or review notes.
- `Clear digest`, `Clear note type`, `Clear reviewer`, and `Clear review shortcuts` reset shortcut-applied provider execution package review filters without changing package evidence, review notes, coverage presets, stale-days, or selected package focus.
- `Active review handoff preview` shows the exact review handoff before copy, including active filters, summary counts, reviewer/category counts, coverage rows, and the generated Markdown text. It is read-only and does not persist a saved view.
- `Coverage queue group totals` shows all visible, reviewed, unreviewed, and stale provider execution package counts for the active review filters. Reviewer, note type, digest, review-state, and stale-days filters update the totals without mutating package evidence or review notes.
- `Focus reviewed`, `Focus unreviewed`, and `Focus stale` on the coverage totals update only the review-state filter. Existing digest, reviewer, note-type, and stale-days filters remain in place, and the shortcut does not persist a saved view or mutate package evidence.
- `Stale review queue`, `Unreviewed queue`, and `Reviewed queue` group the active provider execution package coverage rows for scanning. The groups use the already-filtered report scope and remain read-only.
- Coverage queue row chips show review state, note count, provider target, and latest-review or stale-threshold context inside each grouped package row.
- `Comfortable queue` and `Compact queue` switch only the grouped coverage queue density for local scanning. The control does not change filters, row actions, package evidence, or review notes.
- Empty coverage groups show the active filter scope, including review state, digest, reviewer, note type, execution, and stale-days context where present.
- `Copy group summary` copies the active provider execution package coverage filters, visible package totals, reviewed/unreviewed/stale counts, note count, and grouped queue counts as Markdown.
- `Provider execution package coverage group summary preview` shows the exact Markdown copied by `Copy group summary` before using the clipboard action.
- Summary filter chips show the active provider execution package review scope above the group summary preview and match the preview filter line.
- Summary count chips show visible, reviewed, unreviewed, stale, and note counts above the group summary preview and match the copied summary counts.
- `Download group summary` downloads the same provider execution package coverage summary preview as a local Markdown file without writing to the server.
- The download status chip shows whether the provider execution package coverage group summary has been downloaded locally in the current browser session.
